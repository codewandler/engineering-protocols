# Guard-efficacy review — do the tests and gates actually bite?

Independent review, 2026-08-20, against `main` = `3647f80`. Method: mutation testing by hand in an
isolated worktree. 20 mutations, one live at a time, tree verified clean between each.

Baseline: `cargo test --workspace` = **916 passed, 0 failed, 39 suites, exit 0**.

## Verdict

**13 of 20 mutations were caught, 7 survived, and 2 of the survivors passed the entire five-step
gate — `fmt`, `clippy -D warnings`, `cargo test --workspace`, `schema --check`, `generate --check` —
with a safety property broken.** The repository's newest guards are its best ones: `tests/agreement.rs`
caught a weakened published contract and named the construct, both projections, the file paths and the
keyword class; the conformance `identity` suite caught an id minted from a locator and printed the
offending id next to the key it was derived from; both drift checks and both orphan scans fired in both
directions. The older safety core is where the holes are. Every survivor sits in the part of the system
that decides whether an agent may touch production, and they share one shape: **the rule is correct, the
doc comment states it, and no fixture ever constructs the state in which the rule is load-bearing.**
That is not a gap example-based tests happened to miss — it is the gap example-based tests
systematically miss, because a hand-written fixture encodes the case the author was already thinking
about. Three of the seven survivors (1, 3, 6) are exactly that, and one (20) is an invariant with no
enforcement mechanism at all rather than a weak one. 916 passing tests is a real number; it is not
evidence about the approval path.

## Findings, severity-ranked

### F1 — CRITICAL. A refused approval authorises the action. (mutation 4)

Delete the `ApprovalDecision::Granted` check in `approval_recorded` and an `ApprovalRecord` whose
decision is **`Denied`** unlocks the capability it was recorded against — including `production.write`,
which `protocols/aep/1.yaml:37` puts behind the approval floor for every profile in the repository.
**A human reviewer who reads the change, decides against it, and records a refusal has thereby granted
the production write they were refusing.** The refusal is the authorisation.

`cargo test --workspace`: 916/916. `cargo clippy --workspace --all-targets -- -D warnings`: clean.
`fmt`, `schema --check`, `generate --check`: clean. The full gate is green.

Worth recording precisely, because it is the difference between a guard and an accident: the *first*
form of this mutation did trip the gate — as `warning: unused import: ApprovalDecision`. That is a
dangling-import lint, not a test, and it points at the import rather than at the policy. Doing what
`clippy --fix` tells you to do — delete the unused import — buys a fully green gate. **A lint is not a
guard for a safety property.** No test in `aep-engine::policy` ever constructs an approval with
`ApprovalDecision::Denied`; the module's `approval()` helper hard-codes `Granted`.

*Proptest*: generate an `ApprovalRecord` with an arbitrary `ApprovalDecision` and assert
`authorize(..).is_allowed()` implies the decision was `Granted`. The generator only has to emit one of
two enum variants, so this dies on the first dozen cases.

### F2 — CRITICAL. Invariant 2 has no enforcement mechanism at all. (mutation 20)

AGENTS.md invariant 2 is the most explicit prohibition in the document: "Validated types do **not**
implement `Deserialize`, so the only way to obtain one is to validate. Do not add `Deserialize` to a
validated type to save a conversion." Adding `serde::Deserialize` to `Protocol` compiles, passes
916/916, passes clippy, and passes both drift checks.

**Anyone can hand the engine a `Protocol` that was never validated** — a protocol whose approval floor
is empty, whose declared capabilities do not match its evidence kinds, whose observables are
unparseable — by deserialising it straight off the wire, and the type system will say it is a
`Protocol`. The whole parse-then-validate design rests on a property that nothing checks.

There is no `trybuild`, no `compile_fail` doctest, and no negative-bound assertion anywhere in the
workspace (`grep -rn "trybuild\|compile_fail" Cargo.toml crates/` → no matches). This is the one
finding property testing cannot reach: it needs a compile-time check.

### F3 — HIGH. A profile granting `deployment.create` deploys to production with no approval. (mutation 3)

`needs_approval_floor` is deliberately bidirectional and its own doc comment says why: "a floor on
`deployment.create:production` is violated by granting `deployment.create` for every environment, not
only by granting production specifically." The shipped floor at `protocols/aep/1.yaml:37-39` is exactly
`[production.write, deployment.create:production]`.

Drop the second clause and `Capability::Deploy(Environment::Any)` no longer meets the floor, because
`Deploy(Production).covers(Deploy(Any))` is false. **A profile that writes `allow: [deployment.create]`
— the natural, less specific spelling — ships to production with nobody approving anything.** The more
carefully a profile author spells the environment, the more protected they are; the lazy spelling is
the unprotected one.

Runtime evidence, temporary probe against the shipped floor:

```
unmutated  needs_approval_floor(deployment.create)            = true
mutated    needs_approval_floor(deployment.create)            = false
both       needs_approval_floor(deployment.create:production) = true
both       needs_approval_floor(production.write)             = true
```

`the_approval_floor_is_in_force_for_every_shipped_profile` (`aep-engine/tests/documents.rs:133`) probes
only `Capability::ProductionWrite`, which the surviving direction still covers, so it passes.

*Proptest*: generate `(floor, requested)` pairs over the `Capability` enum including every
`Environment` variant and assert the relation is symmetric under `covers`. Needs the generator to pair
`Deploy(Any)` with `Deploy(Production)` — one variant against one variant.

### F4 — HIGH. `deny` is not a safety envelope, and the test named after it cannot see that. (mutation 1)

This is the root-cause finding, and it is more interesting than the mutation.

`deny_beats_approval_which_beats_allow` (`capability.rs:702`) is named after the full precedence chain
and checks two capabilities:

* `ProductionWrite` — in `allow` + `approval_required`, **not** in `deny` → tests approval-beats-allow
* `SecretRead` — in `allow` + `deny`, **not** in `approval_required` → tests deny-beats-allow

**No capability is ever in both `deny` and `approval_required`** — the only configuration in which
"deny beats require_approval" is observable at all. Grep confirms it: no fixture in `crates/`,
`profiles/`, `principles/` or `protocols/` puts one capability in both sets. So the middle link of the
chain the test is named after has no observable state anywhere in the repository, and swapping the two
branches passes 916/916.

The escape is reachable through the documented composition path. `restrict()` extends **both**
`approval_required` and `deny` from a principle, so: a profile grants `production.write`, principle A
puts it behind approval, principle B denies it. The composed policy holds it in all three sets. With
the order swapped the answer is `RequiresApproval`, and F1's `approval_recorded` then lets a recorded
approval unlock it. **A principle that denies production writes outright is downgraded to "ask
someone", and someone can always be asked.** The module doc calls `deny` "usable as a safety envelope";
nothing tests that it is one.

**Name the class, because it recurs.** A rule whose test cannot reach the state where the rule matters.
Findings F4, F3 and F6 are all this shape, and all three are in code whose doc comment states the rule
correctly. Hand-written fixtures encode the case the author had in mind; the precedence *between* two
mechanisms is never that case, because it requires deliberately constructing a conflict.

*Proptest*: generate a `CapabilityPolicy` by independently choosing, for each `Capability`, whether it
lands in `allow`, `approval_required` and `deny`, then assert `decide()` equals the reference
precedence. Overlaps arrive at roughly one capability in eight, so the first generated case finds it.

### F5 — HIGH. A workflow transition fires on zero observations. (mutations 8 and 9)

Two independent survivors in the three-valued core, which AGENTS.md invariant 5 states as "`Unknown`
is not `False` … Never collapse unobserved to false."

**Mutation 9** changes `Truth::not()` so `Unknown` negates to `True`. The function is three lines, the
doc comment directly above it reads "Kleene negation: `Unknown` negates to itself", and there is no
test for the third row. `.not()` is called only from production code at `predicate.rs:355` and `:469`;
no test calls it at all.

**Mutation 8** makes `Truthy` on an unobserved fact yield `False` instead of `Unknown`.

Runtime evidence for the composition of the two, against an empty fact set:

```
mutated 8    deployment.succeeded      on no facts = False
mutated 8    not deployment.succeeded  on no facts = True
unmutated    deployment.succeeded      on no facts = Unknown
unmutated    not deployment.succeeded  on no facts = Unknown
```

**A guard written `not deployment.failed` passes on a system where nothing has been measured at all** —
the transition is permitted precisely because no verifier has run. Under mutation 8 alone the milder
consequence still bites: the engine can no longer tell an operator "not yet observed, run the
verifier" apart from "observed, and it failed", so they go and debug a deployment that never happened.

No shipped document in `workflows/` or `profiles/` currently uses a negated bare fact, so the
`not`-flip is latent rather than live — but the predicate language accepts it and nothing stops the
next workflow from using it.

*Proptest*: `Truth` has three values. `prop_assert_eq!(t.not().not(), t)` plus De Morgan over
`(a, b)` kills both, and an exhaustive 3×3 table test is cheaper still — this one does not even need a
generator, just a loop over `[True, False, Unknown]`.

### F6 — MEDIUM-HIGH. An audit record can say "refused" and carry the change it made. (mutation 6)

`AuditRecord::validate` guards invariant 15 through `is_rejection()`, which is true either because the
kind says so *or* because the decision does — the doc comment says exactly that. Replace it with
`kind.is_refusal()` and only the kind-based half is enforced.

Runtime evidence, one record with `kind: EntityUpdated`, `decision.allowed: false`, and a
`ChangeRecord`:

```
mutated    is_rejection = true   validate = Ok(())
unmutated  is_rejection = true   validate = Err("[refusal_mutated_state] audit.change: a
           entity_updated record carries a change to entity 01K2R8… , but a refused action must
           not mutate state")
```

**The security reviewer opening the trail six months later finds a record that says the policy refused
the action and also records the rows it changed** — the exact record the audit model exists to make
impossible, accepted by the validator that promises to reject it.

`a_refused_command_that_carries_a_change_is_rejected` builds its fixture from `rejection()`, whose kind
is `CommandRejected` — already a refusal by kind — so the decision-based disjunct is never exercised.
Same class as F4: the rule is right, the state that makes it load-bearing is never constructed.

*Proptest*: generate an `AuditRecord` over the cross product of `AuditKind::ALL` ×
`decision.allowed` × `change.is_some()` and assert `validate().is_err()` iff
`is_rejection() && change.is_some()`. The needed cell is kind-not-a-refusal AND decision-denied, a
two-way combination no hand-written fixture builds.

### F7 — MEDIUM. Two guards catch the break and cannot say what broke.

AGENTS.md requires "Every test asserts a reason" and that tests match on `ValidationCode`s rather than
message text. Two mutations were caught by tests that report only `assertion left == right failed`:

* **Mutation 10**, `kleene_conjunction_keeps_false_ahead_of_unknown` (`predicate.rs:1143`) — prints
  `left: False, right: Unknown` with no reason string. Whoever is woken up has to open the test to
  learn that the invariant is "unobserved must not collapse to false".
* **Mutation 12**, `a_decimal_is_written_as_an_exact_string_because_a_json_number_is_read_as_a_float`
  (`types.rs:818`) — prints `left: None, right: Some("^-?(0|[1-9][0-9]*)…")`. The test *name* carries
  the reason; the failure output does not.

Both are partial successes: the break was caught, the diagnosis was not delivered. Contrast mutation
13's message, which named the construct, both projections, both file paths, the keyword and its class.

### F8 — MEDIUM. `agreement.rs` cannot see a wrong answer all three projections agree on.

This is structural, not a defect, and the crate's own module doc gets close to saying it. `agreement.rs`
compares projections **to each other**. Mutation 12 weakened the single shared mapping so that all
three projections published the same weaker contract — `{"amount": "abc"}` becomes a valid
`billing.invoice.Money` — and `agreement.rs` passed, because the three fragments still agreed. The
mutation was caught by exactly one test: a structural unit assertion in `types.rs`.

The mapping row's real guard is a *rejection* test, and the coverage is uneven.
`crates/ess-gen/tests/schema.rs` does validate documents against the published schema and assert
refusal — `a_uuid_is_refused_unless_it_is_the_canonical_hyphenated_form`,
`a_bytes_field_refuses_a_string_that_is_not_base64` (which even enumerates five near-miss strings).
There is no equivalent for `Decimal`, which is why mutation 12 fell to a structural assertion rather
than a behavioural one. `Uuid` and `Bytes` are guarded behaviourally; `Decimal` is guarded only by
"the node has this pattern field".

### F9 — LOW, but worth knowing. 16 conformance suites, 15 faults.

`aep-conformance` is the strongest thing in the repository and the mapping is **not** luck.
`tests/faults.rs::each_fault_is_caught_by_the_suite_that_exists_to_catch_it` verifies the `caught_by()`
claim directly rather than asserting it in prose; `a_faults_collateral_is_explainable` bounds each
fault's blast radius against a per-fault allowance with a written reason; `every_suite_checks_something`
requires at least four checks per suite; `a_core_claim_is_not_checked_against_audited_properties` keeps
the levels honest. `faulty.rs` also has `each_fault_is_claimed_by_at_most_one_suite`.

The one asymmetry: nothing asserts every *suite* has a fault, and `identity` is the suite no fault
claims — 15 faults for 16 suites. `suites/identity.rs:10-15` argues this is inherent rather than an
oversight ("the wrapper can only perturb what crosses the boundary, and ids are minted inside"), which
is a fair argument. So I tested it from the other side: mutation 11 minted the `EntityId` from the
`EntityLocator` inside the reference backend, and the `identity` suite caught it with the clearest
failure message I saw all day. **The suite earns its keep.** The residual gap is only that its efficacy
is verified by nothing in CI, where the other fifteen suites' efficacy is.

## The gate's completeness — what passes all five steps

`task check` = `fmt-check`, `clippy -D warnings`, `cargo test --workspace`, `schema --check`,
`generate --check`. Concretely, here is the class that passes all five.

**1. Any behavioural change whose imports stay used.** Steps 1 and 2 are style. Mutations 4 and 20
demonstrate the rest. The only reason mutation 4 was ever visible was a dangling import, and removing
it — the fix clippy itself suggests — restores green.

**2. Anything about a type's *derives* rather than its behaviour.** Mutation 20. Nothing in the gate
can observe which traits a validated type implements.

**3. A weakened contract that has been regenerated.** This is the important one, and it is the answer
to "can a real change slip past both drift checks". Both are **tautological by construction**:
`schema --check` compares `schemas/generated/` to what the Rust types currently produce, and
`generate --check` compares `generated/` to what the specification currently produces. Neither asserts
anything about meaning. So:

* Mutation 12 weakened the published contract in `ess-gen/src/types.rs`. `generate --check` failed with
  8 differing files. I then ran `cargo xtask generate` — the command the error message tells you to run
  — and re-ran the gate. **`generate --check`: "projections are up to date". `schema --check`: "schemas
  are up to date". `fmt`: clean.** The only thing still failing was one hand-written unit assertion.
* Mutation 18 deleted an invariant from the normative specification itself. `generate --check` failed
  with 28 differing files; `cargo xtask generate`; both checks green again. The only thing still
  failing was one hand-written docs assertion.

In both cases the drift checks did their job — they detect *unregenerated* drift — and in both cases the
sole surviving guard against the contract actually getting weaker was a single hand-written test. Delete
that one assertion along with the change (which a developer weakening a contract on purpose would) and
the five-step gate is green while the repository publishes a contract that accepts what it used to
refuse. **`schema --check` and `generate --check` are drift detectors, not contract guards, and the gate
has no step that asks whether a published contract still refuses what it promised to refuse.** That is
the wave-3 defect class one level up: last time three copies of a mapping disagreed and no test asked
whether they agreed; this time the mapping has one copy and few tests ask whether the one copy is right.

**4. Anything about the approval path.** Mutations 1, 3, 4 and 6 are all in it, all survived, and the
gate has no step that exercises a refusal end to end.

## Vacuous and self-confirming tests

* **`deny_beats_approval_which_beats_allow`** (`capability.rs:702`) — vacuous for the half of the
  precedence chain that carries the safety weight. See F4. This is the clearest instance in the repo of
  a test whose name is a stronger claim than its body.
* **`Truth::not()` has no test at all.** `.not()` is referenced only from `predicate.rs:355` and `:469`,
  both production. `and` is covered (mutation 10 was caught by four tests); `not`'s third row is not.
* **`a_refused_command_that_carries_a_change_is_rejected`** — passes for the right reason, but its
  fixture reaches only one of the two disjuncts of the property it protects. See F6.
* **~32 bare `assert!(…is_err())` calls** against the AGENTS.md rule "Prefer `expect_err` plus a check
  on the `ValidationCode`". Enumerated across `predicate.rs`, `facts.rs`, `ids.rs`, `entity.rs`,
  `name.rs`, `capability.rs`, `evidence.rs`, `artifact.rs`, `version.rs`, `verification.rs`,
  `consistency.rs`, `project.rs`. **This is mostly a finding about the rule's scope, not 32 bugs**: most
  are `ParseError` paths, and `ParseError` carries no `ValidationCode`, so the rule as written is not
  satisfiable there. Many do pass a reason string (`"upper case"`, `"leading separator"`), which is the
  spirit of the rule. Worth either narrowing the rule to `ValidationErrors` or giving `ParseError` a
  code — but not worth 32 edits as-is.
* **No non-vacuity guard outside `agreement.rs`.** `agreement.rs` prints `compared 11 shared constructs
  over 17 projection pairs` and has a dedicated test
  (`the_agreement_check_compares_the_constructs_the_defect_was_about_rather_than_nothing`) asserting it
  compared something. `aep-conformance` has the equivalent (`every_suite_checks_something`,
  `report.checks() > 0`). Nothing else does. The suites that iterate over a discovered set —
  `ess-gen/tests/docs.rs`, `openapi.rs`, `asyncapi.rs`, `aep-engine/tests/documents.rs` — would pass on
  an empty input set, and `documents.rs` in particular loops over the shipped profiles without asserting
  that it found any.

## Decisions for Timo

**D1 — Fix F1 and F2 now, or schedule them?**
Options: (a) fix both in this wave; (b) fix F1 now, F2 next wave; (c) schedule both.
Cost: F1 is a one-line restore plus a test recording a `Denied` approval — under an hour. F2 needs a
`trybuild` dev-dependency and one compile-fail case per validated type, or a single negative-bound
assertion helper — half a day.
**Default if nobody answers: (a).** F1 is a refusal that authorises; it should not survive the day. F2
is the invariant the whole document layer rests on.

**D2 — Where does property-based testing go first?**
Options: (a) the three-valued core (`Truth`, `Predicate::evaluate`); (b) capability precedence and the
approval floor; (c) `AuditRecord::validate`; (d) all three.
Cost: (a) is the cheapest and kills F5 outright — the `Truth` table is 3 values and needs a loop, not a
generator. (b) needs an `Arbitrary` for `Capability` including every `Environment` variant, and kills F4
and F3. (c) needs an `Arbitrary` for `AuditRecord` over `AuditKind::ALL`, and kills F6.
**Default if nobody answers: (b) first, then (a), then (c)** — (b) covers two CRITICAL/HIGH findings and
is where the reachable production escapes are; (a) is nearly free and can ride along.
Note the ordering argument against my own default: (a) is so cheap it could be done first regardless.

**D3 — Add a gate step that asserts published contracts still refuse?**
Options: (a) require a rejection test per primitive mapping row, enforced by a test over
`Primitive::ALL`; (b) leave `Decimal` as the one structural-only row and accept it; (c) do nothing.
Cost: (a) is a day and closes the gap in F8 and gate-completeness class 3 permanently — it makes the
`Uuid`/`Bytes` pattern the rule rather than the exception. `Bytes` and `Uuid` already show the shape.
**Default if nobody answers: (a).** It is the only proposal here that turns the gate into a contract
guard rather than a drift detector.

**D4 — Require a reason string on every `assert_eq!` in the safety core?**

## Method notes, for reproducibility

* 20 mutations, one live at a time. Files were backed up and restored **by copy**, never by
  `git checkout`, so no uncommitted work could be destroyed. `git status --porcelain` was asserted empty
  between every mutation.
* One process error, disclosed: mutation 11 was still live when mutation 12 was first applied. The
  contaminated run was discarded and mutation 12 was re-run clean (`m12b`); mutation 11's own result was
  unaffected. Every other mutation ran alone.
* Where a mutation survived, a temporary probe was added to obtain a runtime before/after pair rather
  than inferring the consequence from the code. Probes were deleted; findings F3, F5 and F6 quote them.
* Narrow suites were run first where one existed; the full `cargo test --workspace` was run for every
  mutation regardless, because it takes under a minute on this machine.
* The worktree was left clean. `generated/` was rewritten by `cargo xtask generate` twice during
  gate-completeness testing and regenerated from restored sources afterwards.
